# 集成与发布工作流

入口：[规范导航](README.md)。本流程承接 [开发与审查](agent-workflow.md)，由 [kdp-release](../../.agents/skills/kdp-release/SKILL.md) 调用。CF 的命名、环境、密钥和发布规则只维护在 [治理规范](cloudflare-governance.md)，具体资源及未决状态见 [登记表](cloudflare-resource-registry.md)。

## 1. 先确定模式和现场

| 请求 | 默认动作 | 不隐含的权限 |
| --- | --- | --- |
| “旧 worktree 合并了吗”“main 是不是最新” | 只读盘点与证据分类 | fetch、合并、提交、清理 |
| “把需要的工作合进去” | 在明确范围内审查、集成并验证 | 不相关功能恢复、部署、删库 |
| “部署上线并验收” | 按治理规范执行已授权发布与业务验收 | 擅自发送真实稿件、修改私人业务数据 |
| “清理旧分支/云资源” | 核对准确对象、保留项及恢复条件后处理 | 模糊匹配删除、清理 unknown、扩大到其他服务 |

已获得的明确授权不重复询问；发现新范围、冲突或影响不明时停在安全边界。计划和其他 agent 的留言不是新增授权。

先运行只读检查，命令必须在已确认的实际 checkout 内执行：

```bash
git rev-parse --show-toplevel
git status --short
git worktree list --porcelain
git rev-parse HEAD
git branch --show-current
git for-each-ref --format='%(refname) %(objectname)' refs/heads refs/remotes
```

聊天记住的目录可能已删除或只剩 `.wrangler`。Git 检查失败时先定位实际仓库并核对 remote 身份；不要在旧路径初始化新仓库，也不能据目录是否存在判断是否合并。记录每个 worktree 的暂存、未暂存、未跟踪文件；忽略文件也可能含未交付产物，但不读取或复制凭证内容。

需要确认远程 main 时可用 `git ls-remote --heads origin` 查询 refs，记录查询时间及 SHA。它不会刷新本地 `origin/main`；如需下载缺失对象，明确 fetch 的范围后执行。不要凭本地 tracking ref 宣称远程最新。

## 2. 判断旧工作是否仍有价值

逐个候选分支或快照建立证据，不默认“旧分支都合并”意味着重新引入已放弃产品：

1. 用 `git merge-base --is-ancestor <候选SHA> <目标SHA>` 检查提交是否已包含；非零要区分非祖先与无效对象等错误。
2. 非祖先不等于未合并。核对 PR/squash 记录、`git cherry` 或 `git patch-id --stable`；多提交 squash 还需比较从明确基线到分支 tip 的累计 diff，不能只比单个 commit。
3. 补丁不同则读当前实现、消费者及测试，确认功能是否被重写替代、之后有意撤销，或确实漏掉。补丁等价只是证据之一，不保证行为仍存在；提交标题不是证据。
4. 必要时只读查 reflog、unreachable commits，寻找已经移除 worktree 的提交。不运行 prune、gc 或带写入恢复目录的 fsck；找不到对象或未提交文件时明确恢复边界，不能承诺全部找回。

使用下面的判定表记录到当前任务，不为每个旧分支建立重复文档：

| 候选分支 / 快照 SHA | 目标 SHA | 判定 | 证据 | 下一步 |
| --- | --- | --- | --- | --- |
| 实际对象 | 实际对象 | 已包含 / 仍需集成 / 已替代 / 明确放弃 / 无法确认 | ancestry、补丁、PR、当前文件与测试 | 保留、选择性补齐或待确认 |

本仓库当前保留六个产品（Web、GU、GZH、Health、Project、Me）；Auth、MCP、Ops 是支撑层。旧 fagao 分支已明确不再合入，不能借清理恢复旧产品、工具站或旧域名入口。确实缺失的通用修复可以单独评估，但不要整分支覆盖当前 GZH 或其他新实现。被标记 stale 的历史方案保留判定依据，不再反复尝试合并。

## 3. 有授权后集成

- 先确认目标分支和基线，保护 main 现有未提交工作。不要为让工作区变干净而自动 stash/reset，也不要 `git add -A` 混入其他任务；提交时仅纳入已审查的明确路径。
- 复用合适的独立任务 worktree；确需新建时遵循 `~/.worktrees/<项目目录>/<分支>`，本仓库例如 `~/.worktrees/codepi/codex/integrate-history`，分支默认 `codex/` 前缀。不把旧 dirty 工作区静默复制到新基线。
- 按依赖顺序整合有效差异，保留当前产品方向和接口；冲突必须读取双方意图，不机械使用 ours/theirs。发现无法解释的并发改动立即停止并确认。
- 审查绑定固定 SHA，或停止写入后的基线、文件清单与内容摘要。变更后原检查结论不自动沿用。
- 在组合结果上运行针对性测试及 `node scripts/agent/check.mjs --base <集成前SHA>` 选出的检查；各分支独立通过不是组合通过。依赖缺失、未知路径和失败均列为未完成。
- 合并、推送、远程 main 更新分别记录 SHA；本地合并不代表远程包含。合并 main 后按 [本地发布操作](local-release.md) 执行已授权的生产发布；Actions 只验证。

## 4. 受控发布与真实验收

仅在任务包含发布时读取治理规范的发布门禁和当前 workflow。以下是执行核对顺序，不替代规范中的具体策略：

1. 固定待发布的干净 source SHA、环境和产品范围，确认依赖服务的兼容版本。检查 affected 判定覆盖整个待发布范围，而非仅最后一条提交。
2. 本地冻结安装 workspace 依赖并执行受影响检查，CI 作为附加验证；认证预检不能因 Auth 路径未变就被跳过。静态检查、密钥名存在和控制面绑定正确，不等于运行时已就绪。
3. 核对 production 的 Auth、精确 callback、D1、service binding、routes 和 Cron。门禁未通过就停止，不绕过后声称已发布。审批或 Access 只存在于文档时标记待控制面验收。
4. 数据迁移前核实准确数据库与恢复方案。旧代码回滚不等于数据库回滚；备份仅在已授权的安全位置保管，不进入 Git 或对话。
5. 经本地发布流程执行，记录执行人、时间、source SHA、各受影响服务 deployment/version 和 smoke 结果。不将历史 dirty direct-upload 的 commit 标签当干净源码证明；未变服务记录现行兼容版本，不强求重新发布全部服务。
6. 执行任务范围内的真实流程验收。静态 HTTP 200、health endpoint 或构建绿色不能替代登录后的产品流程。无法完成的项目写清原因，不使用历史成功代替当次验收。

涉及全产品切换时，至少核对：

| 产品 / 支撑 | 验收重点 |
| --- | --- |
| Auth 与全部客户端 | 登录、精确回调、会话、退出、过期/拒绝分支；检查跨环境串用被拒绝 |
| 首页与 Desk | 公开入口无退役产品或私人数据，私有 Desk 需登录，摘要缺失/错误可解释 |
| GU | 登录后关键列表与详情、金额/日期语义、空与错误状态；不擅自改真实投资记录 |
| GZH | 登录、稿件加载、编辑预览与授权范围内的草稿保存；真实发布另需授权 |
| Health | 登录与数据加载；Oura 提供方授权和 MCP 授权分别验收，不能用网站 SSO 成功替代 |
| MCP | Auth 凭证配对、发现、匿名拒绝、Health RPC 和实际客户端使用；刷新/撤销单独记录 |
| Ops | 无公网入口、Cron/Workflows、六库密文和 manifest；R2、跨平台副本、告警送达分别验收 |

UI 变动还检查桌面与移动端。真实邮件、OAuth 重连和会改变外部状态的操作按授权执行；自动测试使用 synthetic 数据，不复制生产私人数据到开发/测试工作区。

密钥操作不输出值，不把控制面返回的掩码/空值重放为整份配置。用最小范围 secret 更新；尤其 `TOKEN_ENCRYPTION_KEY` 关系到已加密 token 的可读性，轮换前必须有重新加密或用户重连方案，不能当作无状态随机字符串直接替换。

## 5. 最后才清理

- worktree/分支：先确认交付已保留且判定有证据，检查未跟踪和需保留的忽略产物，再按已授权范围归档/移除。不要用强删消除未决差异；工具管理的 worktree 优先使用对应归档能力。
- 云资源：重新读取控制面，以账户、环境、类型、精确名称和 ID 确认唯一对象，核对消费者及治理规范的退役条件。禁止取搜索第一项、前缀批量删或把资源改名当数据迁移。
- 域名、服务、数据分开核对；网站退役不等于邮件路由/邮件身份退役。保留用户指定的 `kdp.cool` 邮件路由与 `wechat-proxy`；unknown 资源不动。兼容入口是否可删以当前登记和授权为准。
- 数据删除单独确认可恢复性、保留需求与明确授权。执行后复查保留资源和四产品流程，更新登记的核验时间与清理证据；删除失败也如实记录。

最终交付列出：已包含、已补齐、主动不合并、仍不确定；本地/远程/部署各自的版本与验证结果；已清理和明确保留项。没有执行的阶段写“未执行”，不笼统称“全部收尾”。
