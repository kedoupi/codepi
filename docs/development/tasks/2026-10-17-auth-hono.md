## 设计约束（开工前从代码核实）

- 现入口 `src/index.ts` 的 `route(request, env)` 做严格顺序的分发：
  1. `configuration(env)` 解析/校验全部配置，失败抛 `Failure("auth_not_configured", 503)`。
  2. `url.protocol !== "https:" && !(cfg.dev && loopback(url))` → `Failure("https_required")`（默认 400）。
  3. `url.pathname.startsWith("/internal/")`：非 POST → `Failure("method_not_allowed", 405)`；否则 `internal(request, env, cfg, pathname)`，**跳过 origin 检查**（internal 用 Basic 凭证）。
  4. `url.origin !== cfg.origin` → `Failure("origin_not_allowed", 403)`。
  5. 具体路径：`/api/health` GET、`/authorize` GET、`/api/auth/request-otp` 与 `/api/auth/verify-otp` POST（且要求 `Origin === cfg.origin`，否则 403）。
  6. 其余 → `Failure("not_found", 404)`。
- `internal()` 内部对 `/internal/exchange`、`/internal/session`、`/internal/logout` 分发，其余 `/internal/*` → `Failure("not_found", 404)`。
- 入口 `fetch` 的 catch：`error instanceof Failure` → `{error: error.code, status: error.status}`，否则 `{error: "auth_unavailable", status: 503}`，两者都经 `secure()` 加安全响应头。
- Hono 差异与对策（沿用 Health 先例）：
  - `app.onError(e => { throw e })` 让 `Failure` 冒泡到入口统一 catch，保持 `secure()` 包裹错误响应的契约。
  - 405/404 语义由 `route()`/`internal()` 内的守卫承担，所有路由用 `app.all()` 注册，把方法/路径守卫留在 handler 内，与现状一致。
  - Auth 不需要 ExecutionContext（`scheduled` 在入口，fetch 不用 ctx），无需 Health 的 `executionCtx` try/catch 中间件。
- `secure()` 包裹所有正常响应与错误响应；`route()` 里 `/api/health`、`/authorize` 登录页、`/api/auth/request-otp`、`/api/auth/verify-otp` 的成功响应已在各自 handler 内经 `secure()`，入口 catch 的错误响应也经 `secure()`。Hono 化后保持「handler 内 secure + 入口 catch secure」的双层结构不变。
- 定时触发器 `scheduled` 与入口形态不变：`fetch` 委托 `app.fetch`（经 `dispatch()` 保持顺序），外层套现有错误兜底。
