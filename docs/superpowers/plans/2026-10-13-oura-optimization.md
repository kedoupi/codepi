# Oura 优化计划

日期：2026-10-13
状态：路线已由用户选定，已拆解为执行任务；业务实现尚未开始。
范围：`oura/` 及其测试、发布配置。

本文件同时作为后续执行清单。任务状态只能在对应验收证据齐全后更新，
不能把“代码已写”“本地通过”和“生产已生效”混为完成。

## 目标与默认方向

先把 Oura 做成每天愿意打开的个人健康看板：登录稳定、数据可信、
重点清楚、周报有用，常规回归由自动化完成。

本计划按“个人使用优先、暂缓商业化”安排。现有代码支持按用户隔离的 OAuth，
生产实际使用人数尚未核实；不能把“目前个人使用”当成已有访问限制。
保留用户隔离，需要严格私用时再配置服务端账号白名单。

延续现有奶油色、橙色、中文优先的设计，保留 Svelte、Workers、D1 架构。
先调整信息层级与交互，再决定是否需要较大的视觉重做。

## 第一阶段：把稳定性和发布流程闭环

优先级：P0。后续功能开发前完成。

### 工作内容

1. 整理当前修复与测试改动，走 PR 合入；在 GitHub 上验证检查实际执行。
   核对仓库合并规则，让必需检查失败时不能合并。
2. 保持 API 先发布、线上契约检查通过后发布前端的顺序。
   给前后端暴露不含敏感信息的版本标识，记录兼容关系和回滚步骤。
   增加“Worker 丢失路由”和“前端要求的新接口不存在”的失败演练。
3. 将主要浏览器流程迁入 CI 可运行的环境。复用现有隔离数据与用例；
   如需新增浏览器依赖，按仓库约定先确认。保留本机 Ego 脚本作为即时排查入口。
4. 扩展失败场景：授权取消、state 失效或重放、cookie 与 state 不匹配、
   会话过期、refresh token 失效、上游超时、429、数据为空、部分日期缺失。
   优先补回调严格绑定和一次性消费的测试，再修正具体行为。
5. 区分错误状态与恢复动作：
   - 登录过期或授权失效：重新连接 Oura。
   - 同步失败：保留已有数据，显示重试。
   - 服务暂不可用：显示明确状态及请求编号。
   - 功能未开通：显示功能状态，不伪装成网络故障。
6. 保存语言设置时处理请求失败，不能只更新界面却静默丢失服务端保存。
7. 收紧跨域来源、敏感响应缓存和日志输出；错误日志只记录定位所需信息，
   不把上游原始敏感响应拼进用户可见 URL。

### 验收

- 故意移除周报路由后，测试或发布检查必定失败。
- GitHub 至少有一次完整成功记录和一次预期失败记录。
- 浏览器用例覆盖登录态、看板、周报、对比、设置、退出及关键异常分支。
- 登录失效有重连入口，网络失败有恢复动作，设置保存失败有反馈。
- 在预览环境完成一次前后端版本回滚演练。

主要涉及：`.github/workflows/deploy-product-apps.yml`、`oura/scripts/`、
`workers/api/test/`、`routes/auth.ts`、`src/index.ts`、前端 API 调用与错误展示。

## 第二阶段：明确个人使用模式

优先级：P1。先移除日常使用中的无效入口。

### 工作内容

1. 引入服务端明确的个人模式及能力字段。
   个人模式下，为指定账号开放周报和对比，隐藏收费文案与订阅入口；
   不通过开启生产 DEV 登录或伪造 Stripe 订阅来实现。
2. 保留已有多用户数据隔离。若选择严格私用，在服务端限制可接入账号，
   并验证另一个已授权账号不能访问。
3. AI 未就绪期间禁用分析操作，并给出简洁的功能状态；就绪后按能力字段开放。
4. 设置页围绕个人需求组织：Oura 连接状态、数据同步状态、语言、
   时区展示约定、重新连接与退出。同步信息需等待下一阶段提供真实字段。
5. 清理页面里的旧构建标记、占位价格、开发说明与未完成的入口。
   同步修订 README 和 DESIGN 中已经过时的状态。

### 验收

- 个人账号可以完整使用周报与对比，页面没有误导性的收费操作。
- 生产 DEV 登录仍关闭；另一个用户不能读取该账号的数据。
- 所有可点击的功能都有可用结果或清晰状态。
- “个人模式”和“订阅模式”各有独立的服务端权限测试。

主要涉及：`lib/subscription.ts`、`routes/me.ts`、周报/对比授权、
`SettingsPage.svelte`、`PaywallCard.svelte`、`Dashboard.svelte`。

## 第三阶段：让数据同步稳定、可解释

优先级：P1。先保证展示正确，再追求加载速度。

### 工作内容

1. 建立按用户、日期隔离的日汇总存储与同步记录。
   看板、周报、对比读取同一份数据，避免页面之间反复请求同一批上游数据。
2. 同步覆盖近期日期，允许 Oura 后续修正既有记录；
   按需补齐历史窗口，记录最后成功同步时间、数据覆盖区间和最近错误。
3. 区分“最近同步成功时间”和“最新一条数据日期”。
   当天尚无数据时不把上一天数据标成今天；缺失值不当作零。
4. 保留上次成功结果并标明过期状态。按错误类型设置有界超时和重试，
   避免多个页面同时触发重复同步及令牌刷新。
5. 明确 Oura 日记录日期、用户展示时区、滚动七天与自然周的口径。
   当前“本周/上周”使用滚动窗口，需调整文案或计算方式使两者一致。
6. 将每次 API 请求里的建表操作迁移到正式迁移流程。
   先验证旧数据库升级，再接入发布顺序；保留可恢复的数据备份。
7. 记录改造前后的请求次数和接口耗时，按测量结果优化；
   对不完整数据给出覆盖说明，避免输出过度确定的周报。

### 验收

- 同一缓存有效期内从看板进入周报和对比，不重复拉取相同上游窗口。
- 上游暂不可用时能展示最近成功数据，并明确标注时间与过期状态。
- 空数据、只有部分记录、跨月、跨年及时间边界用例通过。
- 多账号数据及同步状态相互隔离。
- 旧库迁移、失败恢复和并发刷新都有测试。

主要涉及：`migrations/`、`lib/schema.ts`、`lib/user-daily.ts`、
`lib/tokens.ts`、`lib/weekly-report.ts`、前端数据状态。

## 第四阶段：围绕每天使用重新整理页面

优先级：P2。依赖个人模式与数据状态确定后实施。

### 页面方向

| 页面 | 首要回答 | 调整重点 |
| --- | --- | --- |
| 今日概览 | 最近一天状态如何，有什么值得注意？ | 三项官方分数、相对个人近期基线的变化、数据日期与同步状态；详细图表放到后面 |
| 周报 | 这段时间有什么变化？ | 三条重点结论、对应指标与日期、数据覆盖、可尝试的日常调整 |
| 趋势与对比 | 变化是偶发还是持续？ | 7/30/90 天统一控件、明确比较区间、少而清楚的图表、可展开贡献项 |
| 设置 | 数据是否连接正常，如何恢复？ | 连接与同步状态、重连、语言和账号操作 |

### 工作内容

1. 先给出桌面和手机关键页面草图，确认信息顺序后实施。
2. 首页首屏只保留最重要信息，减少重复图表与重复解释。
3. 统一加载、空数据、缺数据、过期数据、错误和正常六类状态。
4. 检查手机图表宽度、触摸操作、字号、键盘操作和焦点状态。
5. 统一语言策略：壳与正文保持一致，或明确说明正文语言；
   避免切到英文后出现无解释的中英文混杂。
6. 为每个关键状态保存截图和浏览器断言，避免布局变化破坏操作。

### 验收

- 无需滚动即可看到主要分数、数据日期及状态。
- 周报中的每条变化能追溯到数据与比较区间。
- 375px、768px、1440px 宽度下无横向溢出，关键操作可用。
- 新旧页面使用相同数据时，官方分数和统计结果一致。
- 六类状态均有自动化覆盖，关键导航与操作可用键盘完成。

## 第五阶段：接入有依据的 AI 解读

优先级：P3。稳定性、数据口径和基础周报完成后启动。

### 工作内容

1. 第一版只做“解释已有数据”：哪些指标变化、依据是什么、
   有哪些可选择的日常调整。官方分数和统计计算仍由确定性代码提供。
2. 先准备固定输入与评估样例，再选择模型及调用方式。
   覆盖数据不足、指标矛盾、分数稳定、变化明显等情况。
3. 只发送解读所需的汇总数据；明确第三方处理范围与费用预算。
   展示采用的数据范围、生成时间及结论依据。
4. 输出进行结构与数值校验；缺数据时明确说明，
   不补造生理指标、不生成医疗诊断或治疗方案。
5. 结果按用户和数据版本缓存。调用超时、限流或输出不合格时，
   返回现有模板周报，并标注报告类型。

### 验收

- 数字、日期和比较关系都能与输入核对，出现捏造内容会被测试拦截。
- 用户能分辨模板报告与 AI 报告。
- 模型不可用时看板、趋势和基础周报仍可用。
- 调用量和费用可查看、可限制；测试样例不依赖用户真实敏感数据。

## 执行安排

按三个迭代推进，每轮达到验收门槛后再进入下一轮。第一轮细化到 PR，
后两轮在前置任务完成后细化实现，避免提前锁定尚未验证的方案。
当前不承诺日历工期；测试环境、仓库权限和依赖选择核实后再估算。

| 迭代 | 对应阶段 | 可交付结果 | 前置条件 |
| --- | --- | --- | --- |
| R1 个人稳定版 | 第一、二阶段 | 发布受测试约束，个人账号完整使用周报/对比，错误可恢复 | 整理现有本地修复 |
| R2 数据与体验版 | 第三、四阶段 | 统一数据、可靠同步、清楚的首页和周报、手机体验 | R1 验收；数据口径先于页面实现 |

#### R1-01：当前修复成为可重复验证的基线

- 核对现有未提交改动，只纳入本次 Oura 修复、测试和相关发布文件。
- 重跑 `pnpm test`、`pnpm typecheck`、`pnpm build`、`pnpm test:browser`，
  保存结果并标明哪些针对隔离环境、哪些针对生产。
- PR 上运行无生产密钥的检查；只有合入后发布步骤才取得生产部署凭据。
- 用测试分支中的临时故障证明检查能失败，恢复后确认转绿。
  故障注入只用于测试或预览，不删除生产路由。
- 核对仓库必需检查是否实际阻止失败 PR 合并。权限不足时记录为未完成，
  不能用“workflow 文件存在”替代验收。

完成条件：PR、GitHub 成功/失败检查记录和必需检查状态均可核对。

#### R1-02：发布后能知道线上运行的是哪一版

- 在前后端暴露构建版本和 API 契约版本，不暴露密钥或账户信息。
- 检查 API 版本是否满足待发布前端要求；只匹配 HTTP 状态码还不算兼容。
- 记录发布前版本、发布结果和上一套可用的前后端组合。
- 验证前端发布失败时，已更新 API 仍兼容上一版前端。
- 在隔离预览中演练恢复版本及路由配置；数据库破坏性变更不混入此任务。

完成条件：能够定位版本错位，并按文档恢复到经过检查的版本组合。

#### R1-03：授权异常与网络异常各有恢复路径

- 为 OAuth state 缺失、过期、重放、cookie 不匹配补集成测试；
  回调必须同时满足浏览器绑定与有效的一次性 state 校验。
- 覆盖会话过期、刷新令牌失效、上游超时、429 与错误响应；
  扩展隔离上游，使这些结果可稳定复现。
- 统一前端接口错误分类。明确区分重新授权、稍后重试、服务异常、
  数据为空和功能未就绪。
- 添加有界超时；登录失效清理不可用状态，暂时失败保留本次页面已有数据。
  跨刷新保留历史数据依赖 R2，不提前宣称具备持久缓存。
- 语言设置保存必须检查响应；失败时提示并恢复一致状态或允许重试。
- 同步检查跨域来源、缓存与错误日志，验证敏感内容不会出现在页面 URL。

完成条件：上述场景有自动测试，每个用户可见错误都有准确解释及适用的恢复操作。

#### R1-04：浏览器自动点验纳入每次 PR

- 复用隔离 Worker、D1 和测试数据，浏览器打开实际前端构建。
- 先核实 runner 与现有依赖能否满足需求；新增浏览器测试依赖前集中确认一次。
- 覆盖：进入登录态 → 看板切换 → 周报 → 两种对比 → 语言保存和刷新 →
  退出；再加入 R1-03 的关键错误恢复路径。
- 增加 375px 手机宽度下的主要导航与页面溢出检查。
- 页面脚本异常、关键 API 失败、预期内容未出现均让任务失败，
  保存截图与经过脱敏的诊断信息。
- 固定输入与时间边界；测试成功不依赖真实 Oura、Stripe 或用户逐次登录。

完成条件：GitHub 能无人值守完成主要浏览器流程，且预期故障能使任务失败。
真实第三方授权单独记录验收结果，不以模拟通过替代。

#### R1-05：个人模式以服务端权限为准

- 提议增加个人模式开关与指定账号 ID 配置；默认行为保持兼容，
  缺少指定账号配置时不向所有登录者开放完整权限。
- 提议在 `/api/me` 增加 `capabilities`，表达完整周报、对比、AI、
  账单管理是否可用；字段名称在实现时统一确定。
- 周报和对比接口使用同一份服务端权限判断，前端依据能力字段展示。
  保留真实 `subscribed` 的含义，个人使用权限不写成虚假的付费记录。
- 个人模式不提供收费操作；同时约束服务端账单入口，不能只隐藏按钮。
- 增加权限矩阵：指定个人账号、其他免费账号、已有订阅账号、
  未登录、失效会话；确认都不能跨用户读取数据。
- 账号白名单属于额外的访问范围决策；没有选定严格私用前，
  不因个人模式改动而自动封禁其他已有账号。

完成条件：个人账号能完整查看周报和对比，非目标账号没有意外获得额外权限，
生产 DEV 登录保持关闭，已有数据隔离保持有效。

#### R1-06：界面与能力保持一致

- 个人账号周报/对比不出现付费墙、占位价格和开通订阅按钮。
