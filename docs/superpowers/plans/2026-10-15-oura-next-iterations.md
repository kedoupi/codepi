## 已复现问题的边界

### 周报建议与样本不足相矛盾

实现：`oura/workers/api/src/lib/weekly-report.ts` 的 `buildTips`。

合成输入只有 2026-10-15 一天的三项评分与步数，没有前期样本。
`buildWeeklyReport` 的 summaries 正确写“上周样本不足”，但 tips 的默认分支
仍输出“三项官方分数本周与上周接近”。这是已复现的函数行为；
本轮没有判断它是否已经出现在该账号的生产报告中。

### “近 7 天”按记录数而非日期过滤

同文件 `buildCompareReport(..., "range")` 使用 `sliceLast(sorted, 7)`。
合成输入只有 2026-10-01 和 2026-10-15 两条数据时，“近 7 天”返回的
实际范围是 2026-10-01 至 2026-10-15。需要增加稀疏日期回归，
并检查 HTTP 和 MCP 的周期口径是否一致。

### 默认日期与北京时间不一致

`oura/apps/web/src/lib/health.ts` 的 `dateWindow` 默认取 UTC 日期。
2026-10-15 北京时间 00:30 对应的默认日期为 2026-10-14；
同步计划则明确使用 Asia/Shanghai。页面顶部日期还在组件初始化时固定，
需覆盖页面跨午夜保持打开的场景。

这证明存在日期口径差异，不代表应重写官方记录的 `day`。
方案应区分展示日期、官方归属日、原始时间戳和同步调度时区。

## 三批交付安排

### 第一批：数据正确、发布能守住体验

顺序：O-01/O-02 → O-03/O-04 → O-05/O-06。

- 先修正已复现问题，补缺失样本、跨日、跨月、稀疏数据测试。
- 为“更新数据”定义统一状态和后端任务契约，复用现有同步锁、
  自动任务及预算机制，避免另造第二套队列。
- 将现有浏览器场景迁入适合 CI 的执行环境；保留本机排查入口。
  若需新增浏览器依赖，按仓库规则先确认。
- 告警是运维提醒，不是身体异常告警；先定义条件和接收方式，
  不擅自创建发信或桌面定时任务。
- 检查平台现有备份能力，完成隔离环境恢复演练；未查到仓库演练记录
  不等于平台没有备份。不要对生产库做破坏性恢复实验。
- 核对发布门禁。本轮 GitHub rulesets API 返回 403，无法据此确认
  必需检查已强制执行；不建议为此把私人仓库改为公开。

验收：用户无须逐页点击完成常规回归；日期和样本不足的结论可信；
同步异常可定位、可恢复，关闭页面不丢失已提交的后台任务。

### 第二批：让已经采集的数据真正可读

顺序：O-07 → O-08 → O-09/O-10，O-11 可独立交付。

- 保留已验收首页的视觉方向和公共首页，不再次整体推倒。
- 优先做睡眠与恢复、活动；压力/恢复视图取决于实际记录覆盖。
- 先提供关键页面视觉稿供讨论，再分模块实施。
- 每张图明确回答一个问题；18 类采集数据不对应 18 个导航页面。
- 保留图表的数据表替代，验证缺失、过期、空记录和错误状态。
- 统一中文正文与英文界面策略。当前周报正文主要为中文，
  不把英文壳视为完整英文支持。
- 对图表 CDN 与大序列传输先测量，选择明确的加载、降级或打包方案。

验收：从首页发现变化后，能进入详情、切换日期、理解变化并回到原位置；
375/768/1440px 视口关键操作可用，官方分数和原始数据语义保持一致。

### 第三批：更丰富的解释与更及时的数据

O-12/O-13 依赖前两批的数据、展示和测试基础。

- 不重复建设已有规则解读，也不将“AI 排序”宣传为完整健康分析。
- 扩展解释前确定最小数据范围、第三方处理方式、预算和评估样例。
- Webhook 或更频繁的补采需在实施时核实官方接口与运营成本；
  无论采用哪一种，仍需定时补偿，不能假定事件不会遗漏。

验收：每条解释有可核对的证据，失败时保留可用的规则报告；
更新速度改善有测量依据，不以重复抓取全部历史换取“实时”的表象。
