## 1. 定位与决策边界

### 已确认的方向

> kdp.cool 是 kedoupi（codepi）的个人数字空间，连接我的生活、工作、知识与表达。
> 首页是个人产品入口，各应用构成自己的工作站；博客和知识库沉淀内容，MCP 让这些积累能够被 AI 使用。

- 围绕本人组织产品，不再以广告收入、搜索流量或外部用户增长作为目标。
- 首页介绍本人以及这套个人空间的设计，各应用承担具体用途。
- 健康产品从 Oura 的品牌定位升级为 Health，目标域名为 `health.kdp.cool`。
- 投资理财继续使用 `gu.kdp.cool`。
- 发稿应用应围绕本人的微信公众号重新命名。
- 规划博客、知识库和对外公开的 MCP。

### 本方案采用的默认建议

- 中文为首要表达语言，共享品牌继续使用 `kedoupi（codepi）`。
- 公共首页和私人工作台分开；首页先上线，工作台分阶段完善。
- 博客和公开笔记放在主域名路径内，先使用仓库中的 Markdown 内容。
- 私人资料保留在各应用或后续选定的私有内容存储中，不默认进入公开仓库。
- 保留现有独立应用、统一登录和数据存储；优先修改产品定位与入口。
- 旧工具进入低维护的历史工具区；先保留已有地址，逐项决定是否下线。
- 对外 MCP 首期只读取已明确公开的内容；个人业务数据通过独立授权能力接入。

### 不再承担的目标

AdSense 复审、广告位覆盖、批量扩充工具、为搜索覆盖量增加语言或页面、外部用户注册增长，均退出新路线图。正常的页面可访问性、内容可发现性和已有链接维护仍然保留。

此前 AdSense 相关规则属于旧产品阶段。进入实施时更新 README、AGENTS.md 和现行架构说明，标明新决策生效；旧记录保留为历史，避免继续指导新工作。

## 3. 整体信息架构

```text
kdp.cool                         公开的个人入口
  /                             我是谁、正在做什么、应用、最近内容
  /about/                       更完整的个人介绍与这套空间的来由
  /now/                         当前关注、正在推进的事情、更新时间
  /apps/                        应用目录与访问方式
  /blog/                        已整理成篇的文章
  /notes/                       愿意公开的笔记与主题积累
  /connect/                     联系方式、订阅、MCP 使用说明
  /tools/                       仍可使用的历史工具，次级入口
  /desk/                        后续的本人工作台入口，需登录

health.kdp.cool                 健康
gu.kdp.cool                     投资理财
gzh.kdp.cool                    公众号工作台，域名候选
auth.kdp.cool                   统一登录
mcp.kdp.cool                    后续统一 MCP 入口，域名建议
```

这是目标架构，不要求第一版生成所有栏目。没有真实内容的栏目暂不进入导航；不放占位文章、不编造个人经历和使用数据。

`/desk/` 是建议的用户入口。首版主站继续静态输出；到私人工作台阶段再增加明确的鉴权服务端路径或同域 API。不得把私人内容写入 Astro 静态产物，也不得依靠前端隐藏实现访问控制。

## 4. 首页结构

首页的阅读顺序为：认识这个人 → 理解他关心什么 → 看见他的应用和内容 → 找到进一步了解或连接的方式。

### 4.1 顶部导航

- 左侧：`kedoupi（codepi）`，回首页。
- 主导航：应用、文章、笔记、近况、关于。首版只展示已有内容的项。
- 右侧：低强调的“我的工作台”入口；未登录时进入统一登录流程。
- 移动端优先保留身份、文章和应用入口，其他导航收进菜单。

首版不在公共导航中调用私人业务 API。若私人工作台尚未上线，该位置可先使用“应用入口”，指向 `/apps/`，不显示失效登录按钮。

### 4.2 首屏：我是谁

内容组成：

1. 名字和个人标识；头像或形象素材由本人提供或确认。
2. 一句个人描述。
3. 一小段说明这套空间如何连接生活、工作和思考。
4. 两个入口：“看看我做的东西”“读我的文章”；没有文章时使用“了解我”。

可供调整的文案：

> 我是 kedoupi（codepi）。
> 我把生活里关心的事，做成可以长期使用和积累的东西。
> 这里记录我的思考，也连接我的健康、投资与内容工作。

这只是文案草稿，不补写职业、资历、个人经历等未知信息。

### 4.3 近况：我最近在关注什么

展示 2–3 条本人选择公开的近况，附真实更新时间。例如“正在整理个人数字空间”可以使用本次已确认的事实；其他条目由本人提供。

此处链接 `/now/`，初期手工维护。它不自动展示睡眠、持仓、收益或待审稿件。

### 4.4 应用：我用什么管理这些事情

优先展示三个领域，每项包含：名称、一句用途、当前状态、访问方式。

| 首页展示 | 用途表达草稿 | 点击行为 |
| --- | --- | --- |
| 健康 Health | 理解自己的睡眠、恢复与长期健康变化 | 查看公开简介或进入本人应用 |
| 投资理财 GU | 记录持仓、研究和决策，持续复盘 | 查看公开简介或进入本人应用 |
| 珂抖屁 · 公众号工作台 | 从选题、稿件到审核与发布，整理内容工作 | 了解公众号；管理入口单独标为“本人使用” |

公开简介可先在 `/apps/` 内以章节实现，无需每个应用再造完整营销站。

访客应能看懂产品，即使没有访问私人应用的权限。展示界面时使用经过确认的脱敏素材，不直接截取真实个人数据。

### 4.5 内容：最近写下来的东西

- 文章：最近 2–3 篇，展示标题、摘要、日期。
- 笔记：最近 3–5 条，展示标题、主题、更新时间。
- 没有真实内容的模块不渲染；第一版不为凑首页批量生成文章。
- 文章和笔记采用共同的主题标签，便于之后检索和 MCP 读取。

### 4.6 简短说明：这套空间如何连接

用一段话解释网站、应用、知识积累和 AI 的关系。可以配一幅简单结构图；不在首页展示 API 参数、授权协议或技术配置。

建议表达：

> 我希望这里的记录能持续积累，也能被我使用的 AI 理解和调用。
> 公开的文章与项目会逐步通过 MCP 提供，个人记录则由我选择如何授权。

MCP 尚未发布时标记“建设中”，不提供假连接按钮。

### 4.7 页脚

包含关于、联系、内容订阅（具备内容后）、隐私说明、工具存档，以及与实际实现一致的版权和更新信息。

删除广告支持、永久免费工具站等旧定位文案。隐私说明同时适配公共内容和需要登录的应用，分别说明实际数据处理方式。

### 首页完成标准

- 第一次访问可以迅速理解这是谁、关注什么、做了哪些东西。
- 三个主要应用的用途和访问权限清楚。
- 手机端可以顺畅阅读与进入应用。
- 无虚构内容、无空栏目、无广告脚本、无私人数据进入公开页面。
- 不依赖 Health 改域名或统一 MCP 完工才可上线。

## 5. 子产品定位与迁移

### 5.1 Health：从数据来源升级为健康领域

定位：本人健康记录与回顾空间。当前主要数据来源为 Oura，先保证已有功能稳定；其他设备、运动记录、体检和手动记录只作为后续扩展方向。

首轮范围：

- 产品展示改为 Health / 健康，目标域名 `health.kdp.cool`。
- 保留现有睡眠、恢复、活动数据与同步能力。
- 在连接设置与数据来源中保留 Oura 的真实名称。
- 历史记录、现有数据身份、授权和同步任务保持连续。

技术名称第一轮保留：`oura/` 目录、`oura-kdp` Pages 项目、`oura-kdp-api` Worker、D1 库、内部 `oura` client ID、已有 Cookie 和 MCP scope。它们不要求随产品名称一起更改。

迁移步骤：

1. 记录当前生产域名、Pages 绑定、Worker 路由、登录回调、Oura 提供方回调和 MCP 连接清单；建立数据和关键配置的恢复依据。
2. 将新域名关联到现有 Pages 项目，配置 DNS/TLS，并为新域名补齐 `/api/*`、`/mcp`、`/oauth*`、`/.well-known*` Worker 路由。
3. 在统一登录中心精确登记新回调，保留旧回调；检查前端 Origin 校验、退出、回跳和跨域请求规则。
4. 核对 Oura 开发者后台的回调配置能力，选择过渡期回调方案；不得仅改 `OURA_REDIRECT_URI` 就假定外部授权已生效。
5. 先在新域名验证网页登录、历史数据、同步、重新连接 Oura、退出和会话到期；SSO 可用于建立新域名会话，不承诺旧域 Cookie 自动迁移。
6. 验证新旧 MCP 地址各自的发现元数据、授权、调用、刷新和撤销。新地址按重新连接并授权设计，不承诺旧连接无感迁移。
7. 更新首页入口、应用文案、部署检查脚本和文档；观察一次实际定时同步和真实使用流程。
8. 验收通过后，旧域普通页面先使用可回退的临时跳转；确认稳定后再考虑永久跳转。认证、OAuth 回调、MCP 和发现端点不套用整站跳转。
9. 旧协议端点的退役以连接迁移情况为依据；个人连接都迁移并验证后，才关闭相应兼容路径。

过渡期间特别处理 `FRONTEND_ORIGIN`：当前是单一值，不能仅增加路由就假定两个域都能完成全部流程。需要明确双域允许列表或区分旧域兼容行为，避免授权跳回错误域名。

恢复方式：恢复主站旧入口和旧域配置，保留原数据与客户端身份；不删除新旧域名下的历史数据、不关闭统一登录来绕过问题。浏览器跳转的回退与 MCP 客户端的重新连接分别处理。

### 5.2 GU：保留域名，明确用途

定位：本人的投资理财记录与复盘工作台。

首轮范围：

- 保留 `gu.kdp.cool`、现有登录和数据同步方式。
- 页面名称表达为“投资理财”或“投资工作台”，GU 保留为标识。
- 公开介绍说明它做什么；实际持仓、金额、风控和研究记录仍需授权。
- 延续数据来源、更新时间和待核实状态，避免把界面刷新当作数据已验证。
- 后续按实际使用补充研究笔记和决策复盘，不在此次迁移中扩张业务功能。

验收：原有登录、数据查看和同步流程不受主站改版影响；公共页面不泄露投资数据。此规划不涉及投资建议或交易执行。

### 5.3 公众号应用：品牌围绕公众号，功能围绕内容工作

建议产品名：**珂抖屁 · 公众号工作台**。

建议域名：`gzh.kdp.cool`，待本人确认。该名称是新入口建议，不恢复已退役的 `gzh-preview` 应用。

首轮范围：

- 保留现有稿件、状态、预览和人工审核流程。
- 公开入口说明公众号内容与阅读方式；“进入工作台”只服务有权限的使用者。
- 先改展示名称，域名可在独立批次迁移。
- 既有 `fagao/` 目录、Pages 项目和数据库先保留。
- 不自动接入微信发布 API，不把“审核通过”扩展成自动发布。

迁移按 Health 的网页登录与域名步骤执行，另行核对：旧预览链接、同域稿件路径、移动端通读后审核、状态流转、历史书签，以及可能仍指向发稿台的 `gzh-preview.kdp.cool` 兼容入口。

回退保留 `fagao.kdp.cool` 可用，不同时移动数据。域名未定不阻塞其他阶段。

### 5.4 博客与知识库：同一套内容，按用途呈现

博客承载整理完成的表达；笔记承载允许持续修改的知识积累。共同主题可以连接相关文章和笔记，不要求先建立复杂知识图谱。

公开内容首期建议字段：

```text
id / slug / title / summary
kind: article | note
topics
publishedAt / updatedAt
status: draft | published | archived
visibility: public | private
source / relatedIds（可选）
```

- 只有 `published + public` 内容进入公开构建、列表、RSS、搜索和公共 MCP。
- `private` 字段不等于允许把私密正文放入公开仓库；私人源文件必须在访问控制明确的存储中。
- 稳定 `id` 用于跨文章、笔记和未来 MCP 引用；修改标题不必修改身份。
- 先使用现有 Astro 项目和 Markdown；如实现需要增加依赖，再按仓库规则单独确认。
- 第一期手工维护主题和相关内容；先解决写入、修改、发布和找回。
- 私人知识库的编辑入口、附件和导入方式，在真实使用后单独确定，不立即建设通用 CMS。

### 5.5 旧工具和广告体系

| 旧内容 | 建议处理 |
| --- | --- |
| 主站金融计算器与 guides | 首页让出位置，保留已有 URL；从工具存档访问 |
| calc / convert / text / dev / ai | 暂停扩张，保留仍有用的工具；退出主导航 |
| AdSense 注入与广告占位 | 先关闭广告加载和渲染，随后清理已无调用的专用组件与样式 |
| `ads.txt`、CSP 中广告来源等 | 按实际用途做后续清理，修改前检查引用和共享影响 |
| 旧“免费、广告支持”品牌文案 | 替换为新的个人空间叙事；不能继续把历史承诺用于所有产品 |
| 复审专用 `noindex` 和 sitemap 策略 | 按保留、公开、归档、私有状态逐项梳理，不直接全量反转 |
| 旧部署项目 | 初期保留；只有明确退役后再处理资源 |

旧页面有对应内容时再做准确跳转；没有替代内容且确认下线时返回明确的退役页或 410，不把所有旧地址重定向到新首页。

去广告涉及共享布局，必须检查六个静态站点的实际消费范围并验证构建。内容保留不意味着继续追求流量，也不意味着继续承诺无人维护的计算结果准确；保留清单应包含维护状态。

## 6. 个人工作台

### 第一版：统一入口

- 提供 Health、GU、公众号工作台和内容管理位置的快捷链接。
- 复用统一登录；不要求第一版跨应用读取所有数据。
- 不增加第二套个人账号或用户注册流程。

### 第二版：只加入每天真正需要的摘要

候选：健康数据是否已同步、投资数据最近更新时间、待审稿件数量、最近笔记。

每个摘要要具备来源、更新时间、失败或过期状态和进入原应用的链接。哪些指标显示，由实际使用决定，不把三套完整看板复制到首页。

实现要求：

- 在工作台服务端验证身份，并以明确的只读权限调用各领域接口。
- 不能假定应用间 Cookie 可直接共用；在现有 SSO 上明确工作台客户端和服务端访问边界。
- 私人响应不进入共享缓存、静态构建、RSS 或公共内容索引。
- 一个应用不可用时，其摘要单独显示失败，不使整个工作台失效。
- 首轮不新建跨应用数据仓库，不复制完整业务数据库。

## 7. MCP 的落地路线

### 7.1 公共 MCP

目标：外部 AI 能读取本人明确公开的介绍、项目、文章和笔记。

建议入口：`mcp.kdp.cool/public/mcp`。这是候选地址，不代表已创建服务。

首期候选能力：

- `get_profile`：公开个人介绍。
- `list_projects`：公开应用与项目。
- `search_public_content`：按主题或文本搜索公开文章和笔记。
- `get_public_content`：按稳定 ID 获取正文、来源地址和更新时间。

工具名称是产品草案，实施时再定协议版本、schema 和客户端兼容性。公共 MCP 与网站使用同一份公开内容清单，避免一份内容维护两套。

发布、撤回和可见性变更应同步更新网页、RSS、搜索及 MCP；清理可控缓存，但不承诺撤回外部客户端已保存的副本。

### 7.2 本人授权使用的 MCP

健康先复用现有 MCP。投资和内容工作流在接口稳定、实际需要明确后逐步接入。

长期可考虑 `mcp.kdp.cool/personal/mcp` 作为统一入口；是否聚合在验证现有健康连接后决定。统一入口如落地，必须有明确的领域授权适配，不透传任意客户端 token 到各应用。

- 网站 SSO、Oura 提供方授权、MCP 客户端授权继续区分。
- 健康、投资和稿件分别定义权限，能够独立撤销。
- 只读能力先行，保留来源、时间、缺失和过期状态。
- 首期不包含交易、公开发文、删除原始记录等写操作。
- 后续写入从“保存草稿”“追加笔记”等具体用例开始，单独设计确认、重复提交处理和操作记录。

这一阶段的验收必须包含：公共接口无法访问私人内容；未授权、已撤销和权限不足的连接均不能读取相应数据。隐藏工具名称不构成权限控制。

## 8. 分期执行与验收

各阶段按交付物验收，耗时在实施前结合实际资源核定，不将日历日期当作上线承诺。

| 阶段 | 主要交付 | 前置依赖 | 完成条件 |
| --- | --- | --- | --- |
| P0：确定边界 | 页面清单、公开/私有清单、旧入口处置表、个人文案初稿、更新现行项目说明 | 本方案方向确认 | 实施人员能判断每项内容放在哪里、是否公开；未定名称不阻塞其他工作 |
| P1：个人首页上线 | 新首页、应用介绍、关于/近况中的实际内容、旧工具次级入口、停止广告展示 | P0 | 手机与桌面可用；原应用可达；旧链接有去向；没有广告与私人数据 |
| P2：应用身份迁移 | Health 新域名与名称、GU 表达统一、公众号展示名称和选定域名 | P0；与 P1 可部分并行 | 各应用逐个验收登录、业务、旧链接和恢复路径；Health 另验 MCP 与同步 |
| P3：内容积累可用 | 博客、公开笔记、标签、RSS、发布流程、稳定内容 ID | P1 的主站结构 | 本人能够完成一篇真实文章和一条真实笔记的创建、修改、发布、撤回 |
| P4：工作台可日用 | `/desk/` 登录入口、快捷链接、经选择的少量摘要 | P2 的应用身份稳定；快捷入口可提前 | 登录和退出正确；摘要来源与时效清楚；无跨域数据泄露 |
| P5：公共 MCP 上线 | 公共内容接口、使用说明、客户端接入验证 | P3 | 能通过实际客户端查询并引用公开内容；撤回同步生效；私人内容不可达 |
| P6：个人 AI 能力整合 | 健康、投资、笔记的授权只读访问；按需聚合 | P2、稳定的领域接口 | 授权范围与撤销有效；真实使用有价值；不依赖重复维护数据 |

建议执行顺序：

```text
P0 → P1 → P3 → P5
  └→ P2 → P4
        └→ P6
```

P2 内部顺序：Health → GU 展示调整 → 公众号。每个应用独立上线和验收，不同时切换所有生产入口。

### 第一批可直接拆成实施任务的内容

1. 更新当前项目定位文档，解除旧 AdSense 路线对新主站的约束。
2. 建立一份轻量应用清单，集中维护显示名称、用途、入口、访问方式和状态。
3. 编写个人首页与应用介绍，复用现有 Astro、品牌和必要组件。
4. 关闭广告加载与展示，检查旧广告文案、首页结构和共享组件影响。
5. 整理旧 URL 清单；首轮保留旧工具页面和现有应用入口。
6. 完成六个静态站构建与首页桌面/移动端检查。

第一批不依赖新域名、CMS、私人数据聚合或新 MCP 服务；可以尽早交付一个准确表达新定位的主站。

### 验证顺序

1. 主站：检查内容真实性、导航、旧链接、语言入口、404、键盘和手机使用。
2. 共享层：构建 `web`、`calc`、`convert`、`text`、`dev`、`ai`；修改逻辑时运行相关现有测试。
3. 应用迁移：运行所涉及应用的现有测试、类型检查与构建。
4. 生产切换：逐项检查 DNS/TLS、实际部署版本、统一登录、回调、真实业务读写范围和退出。
5. Health：额外验证历史数据、定时同步、提供方重新连接和 MCP 生命周期。
6. 内容与 MCP：检查草稿/私密内容不出现在公开产物，发布与撤回在各出口一致。

构建通过只证明本地代码检查通过，不证明线上绑定、邮件、外部 OAuth 和客户端连接可用。涉及实际收信、业务写入或连接授权的验收，按实施时的明确授权范围执行。

## 10. 如何判断这套规划有效

采用少量个人使用标准，不建设增长分析平台：

- 首页是否准确表达本人，并能找到主要应用和内容。
- 本人是否在一周真实使用中持续通过这些入口工作。
- 是否能方便地记录、找回和修改一条知识，而非只完成页面建设。
- 应用是否保留原有数据连续性，并清楚说明数据来源和更新时间。
- AI 能否检索到正确的公开内容，并在授权范围内读取私人记录。
- 新增一项内容或应用是否需要到多个地方重复维护。

阶段结束时记录实际使用问题，决定下一阶段范围；不以页面数量、接入数量或功能数量判断进度。
